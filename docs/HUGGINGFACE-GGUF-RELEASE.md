# Prepare the Imagine GGUF release for Hugging Face

## K–6 model published and verified, 2026-10-25

The [completed K–6 benchmark](RUNPOD-GGUF-K6-20261025.md) and [verification receipt](../experiments/runpod-k6-gguf-validation-20261025.json) are committed at `7d942c7fc09a020704c9ffeae436e654cd1f4ea6`. The candidate archive, every member, source identity, inference contract and paired comparison passed local verification. The K–6 weights and updated README are now public under Apache-2.0 at [christian-bick/EduGraph-Classifier-Qwen3.8-27B-GGUF](https://huggingface.co/christian-bick/EduGraph-Classifier-Qwen3.8-27B-GGUF/tree/140480b1d3893f0fb678a6f2d0f92103a60a936b), immutable revision `140480b1d3893f0fb678a6f2d0f92103a60a936b`. Anonymous readback verified all eight release files: both GGUF LFS hashes and sizes, and the exact bytes of every smaller file. The prior revision and existing `.gitattributes` were preserved.

The successful retry, `edugraph-20261025-qwen38-27b-k6-gguf-v2`, achieved **43/64 exact-set match (67.19%), 95.38% label micro-F1 and zero invalid outputs** in each of two repeats. All 64 response texts were identical between repeats. The selected NF4 source achieved **47/64 on the same checkpoint-selection images**: the exported serving configuration loses four exact matches, so publication does not establish production readiness. No matching standalone BF16 diagnostic was run. The separate 306/414 final result belongs to NF4; GGUF has not been evaluated on that cohort.

The [release recipe](../experiments/hf-gguf-release-qwen38-27b-k6-v1.json) pins the verified epoch-2 adapter, dataset `v0.31.0-01`, ontology `0.31.0`, the base model, execution code, immutable benchmark record and candidate hashes. It preserves the established BF16 merge, Q4_K_M language weights and BF16 vision projector. Context, logical batch and microbatch are configured to 4,096 tokens; the batch setting prevents llama.cpp from capping the larger microbatch. Validation used concurrency one, two warmups, two repeats, 512 output tokens, greedy generation, RGB JPEG quality 75 and schema property order `areas, scopes, abilities`.

The model card describes the 2,330-image training corpus as covering **in-scope Common Core State Standards for Mathematics from Kindergarten through Grade 6 (K–6)** and links the [Coverage Explorer](https://coverage.edugraph.io) for competency coverage and exclusions. Corpus scope does not establish mastery of every standard. Official validation omits 147 of 403 training labels; 224 images across selection and final validation reuse previously inspected assessment bytes. These are regression measurements. Realized-range labels, label completeness and a fresh assessment remain follow-up work.

The Secure L40S retry took **48m33s from the recorded provider start to completion**, costing approximately **$0.92 for compute and running disk combined**. The Pod's absence was confirmed by HTTP 404 after successful termination. This estimate includes startup and excludes GCS and taxes; it is not an invoice. The [failed first attempt](RUNPOD-GGUF-K6-STARTUP-20261025.md) remains separate: approximately **$0.72**, plus stopped-storage charges until its authorized cleanup at **17:55 UTC on October 25**. The [cleanup receipt](../experiments/runpod-k6-gguf-cleanup-20261025.json) confirms deletion of that Pod and its attached 350 GB volume; it no longer incurs storage charges.

The [publication receipt](../experiments/hf-gguf-publication-qwen38-27b-k6-v1.json) records the verified revision, predecessor, file hashes and sizes. One guarded Hub commit published the reviewed weights, inference contract, README, provenance and pinned Apache-2.0 license, using predecessor `477e3caf32eced2a9e002ead1edccc9a5c458f0c`. Imagine/GCP production continues to use the previous release.

For subsequent releases, `hf-gguf-release` accepts optional `context_tokens`, `ubatch_size`, `benchmark_record_path` and reviewed `coverage`/`limitations` paragraphs in the release recipe. These fields are retained in public provenance. Omit `evaluation.bf16_exact` when no matching BF16 diagnostic exists. Historical recipes default to a 2,048-token context and 1,024-token microbatch; the card derives logical batch as `max(2048, ubatch_size)`. Local validation of this release support passed 378 tests with 95.83% coverage and `uv lock --check`; the completed benchmark supplies the separate live quality and hardware evidence.

## Previous published release

The selected repository [`christian-bick/EduGraph-Classifier-Qwen3.8-27B-GGUF`](https://huggingface.co/christian-bick/EduGraph-Classifier-Qwen3.8-27B-GGUF/tree/477e3caf32eced2a9e002ead1edccc9a5c458f0c) was published publicly under Apache-2.0 on 2026-10-06 at immutable revision `477e3caf32eced2a9e002ead1edccc9a5c458f0c`. The [publication receipt](../experiments/hf-gguf-publication-qwen38-27b-v1.json) records every released file hash and size. The v4 L40S candidate also remains in GCS; publication itself created no GCP deployment. The model was subsequently promoted to Imagine production, as the [cutover receipt](../experiments/imagine-27b-default-cutover-20261022.json) records. The [benchmark record](RUNPOD-GGUF-BENCHMARK-20261004.md) explains the 37/64 GGUF validation result, its comparison with merged BF16 and NF4, and the request-order correction required to reproduce it.

The recipe pins execution code at `0a6cc246889ea1087df88126d26d5642e9b285a2` separately from the later [immutable benchmark record](https://github.com/christian-bick/edugraph-classify/blob/60e2e2b710b262cc527137ffc75aa61fe868d679/docs/RUNPOD-GGUF-BENCHMARK-20261004.md), which includes the corrected v4 result.

`experiments/hf-gguf-release-qwen38-27b-v1.json` pins the v4 candidate archive's full SHA-256 and byte length, the six source-file hashes, the source training and model revisions, and the evaluation report. The local `hf-gguf-release` command checks the archive and every member before creating a release directory. It rejects extra, duplicate, non-file, or renamed tar members; it never extracts arbitrary paths. The release contains only `model-Q4_K_M.gguf`, `mmproj-BF16.gguf`, `chat_template.jinja`, `prompt.json`, and `closed_schema.json`, plus a generated model card, `provenance.json`, and the approved upstream `LICENSE`. Operational `manifest.json` and `candidate.json` are verified but deliberately omitted from the public staging area. The source GCS URI, Pod and local paths are not copied into the card or provenance.

The exact base checkpoint, [`Qwen/Qwen3.8-27B` at `1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`](https://huggingface.co/Qwen/Qwen3.8-27B/tree/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0), declares `apache-2.0` and includes its [Apache License 2.0 text](https://huggingface.co/Qwen/Qwen3.8-27B/raw/1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0/LICENSE), including the Alibaba Cloud copyright notice. The verified local copy is `experiments/licenses/Qwen3.8-27B-1d4bf0f-LICENSE` (SHA-256 `bbedc3fda3305820b977265f01b8619d87570a6739de3a5582c3464840f1e57a`). The owner has selected Apache-2.0 for this EduGraph weight release. The model card must identify that exact upstream checkpoint and describe the EduGraph fine-tuning, merge, conversion, and Q4_K_M quantization as modifications. The project intends to use Apache-2.0 for future model releases as well, subject to verifying each model's exact upstream weights and their redistribution requirements. The repository's code license alone does not establish rights to redistribute a future set of weights.

Use a locally available, verified copy of the candidate archive. Obtaining the 17.5 GB source archive from GCS and uploading a Hub repository are separate provider actions, outside this command. Run from the repository checkout:

```powershell
uv run --no-sync edugraph-classify hf-gguf-release `
  --recipe experiments/hf-gguf-release-qwen38-27b-v1.json `
  --candidate-tar <path-to-v4-candidate.tar> `
  --model-license-id apache-2.0 `
  --model-license-file experiments/licenses/Qwen3.8-27B-1d4bf0f-LICENSE `
  --output artifacts/hf-gguf-release-qwen38-27b-v1
```

The command copies the supplied upstream text to `LICENSE`, sets the card's Hub license metadata to `apache-2.0`, and records the chosen ID in provenance. Supplying only one license option fails. Review the staged `LICENSE` against the pinned upstream file and its SHA-256 before publication; this is the actual weight-license source, distinct from the repository's code license. Running without the two license options creates a **DRAFT — DO NOT PUBLISH** card and `DO_NOT_PUBLISH_LICENSE_PENDING.txt`, which must never be uploaded as the release. A passing command is a staging check, not a substitute for release review.

Review the complete staged directory before any upload. In particular, confirm the two GGUF file hashes, that the card describes the **same 64-image original validation cohort** (GGUF 37/64, merged BF16 40/64, selected NF4-plus-adapter 43/64), and that the separate **181/250 final assessment belongs only to NF4 plus adapter**. Check the `llama-server` command and request contract in the card, including JPEG quality 75, a one-image user message, greedy generation, JSON response format, and request-time `areas, scopes, abilities` schema property order. The latter fixed a large v3-to-v4 accuracy difference without changing the GGUF weights.

The command is preparation only: it has no Hugging Face SDK, authentication, repository-creation, or upload path. The separate approved publication used these exact staged files and preserved the card, license, and provenance together. Any new upload or GCP promotion remains a separate reviewed provider step. The previously deployed 4B model used older dataset and ontology releases, so a paired score against it is not a promotion gate or a useful quality claim for this release. Do not substitute its legacy card or report its score as this GGUF model's result.
