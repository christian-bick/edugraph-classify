# Imagine baseline promotion: Qwen3.8-27B GGUF

This is the promotion path for the verified EduGraph classifier candidate and the chosen classification-only Imagine rollout. It records local preparation and the gates for a public model release and a GCP cutover; it does not authorize a provider operation. The current `edugraph-predict` revision remains `edugraph-predict-00005-59s` on the 4B GGUF, with 100% of traffic and image digest `sha256:6c0080fc4ff1ddda4295916a44ec6cc8e715ab3d01d3b5172b7def6c5cdfb9f0` as the rollback anchor.

## Serving and application contract

The new [production Dockerfile](../containers/gcp-gguf-inference/Dockerfile) builds the same pinned llama.cpp release and verifies the language GGUF, projector and template at image-build time. Its default server flags match the benchmark's concurrency-one route: 2,048 context tokens per slot, 1,024 microbatch, one slot, all GPU layers, `--fit off`, and the fixed Jinja template. Build with the curated release directory as the context so no remote `ADD` or floating model URL enters the image. The large image is a deliberate first canary route compatible with the current production pattern; Google [recommends Cloud Storage for models of this size](https://docs.cloud.google.com/run/docs/configuring/services/gpu-best-practices), so cold-start/import time and storage cost must be measured before adopting it as the permanent path.

Imagine currently sends an image-only request and expects uppercase `Area`, `Scope`, `Ability` keys. The validated request instead contains `prompt.json`'s user text, an RGB JPEG quality-75 image data URL, an ordered copy of `closed_schema.json` with `areas, scopes, abilities`, temperature zero, `max_tokens=512`, `enable_thinking=false`, and no stream. The client must validate lowercase identifiers against ontology v0.30.0 and adapt them to the existing URI-bearing application response. Keep this new contract opt-in until the new prediction revision is ready; the deployed 4B contract must continue to work.

Imagine currently loads ontology v0.5.0 and an old embedding model/entity map. In the GGUF v4 reference round, 88 of 126 distinct predicted identifiers were absent from v0.5.0 and every case had at least one absent identifier. The immutable [v0.30.0 ontology release](https://github.com/christian-bick/edugraph-ontology/releases/download/v0.30.0/core-ontology-math.rdf), SHA-256 `6372ccb30056aac760a3883f933cdfc6b1bbf563a68aeecd5f03a03da3f3bdcb`, contains all 680 schema labels; its individual URIs use `http://edugraph.io/edu/<Label>` rather than the legacy `http://edugraph.io/edu#<Label>`. Validate and display all predicted identifiers under this ontology; do not silently drop new ones or treat unrelated ontology relations as logical entailment.

The currently served Imagine web bundle sends uploads to `/classify_and_search` and offers Find Similar through `/search`, so the public demo does invoke the embedding-backed path today. The chosen update is classification-only: promote the isolated backend's opt-in GGUF request and v0.30 ontology contracts with `SEARCH_MODE=disabled`, then ship the matching opt-in web build that calls `/classify` and hides Find Similar. Both components must move together; disabling backend search alone would make the current web upload flow fail. The local classification-only canary package pins and verifies the prompt, schema, and RDF without requiring an embedding or content index. Neither isolated branch has been deployed. Rebuilding and evaluating a compatible embedding and content index is a separate future task and does not block the classifier publication or classification-only canary.

## Local-prepared Cloud Build route

This route has only been prepared and tested offline; no paid Cloud Build job, Artifact Registry push, or Cloud Run revision has started.

The local Docker daemon is unavailable. The reviewed [Cloud Build configuration](../containers/gcp-gguf-inference/cloudbuild.yaml) submits only the small `containers/gcp-gguf-inference` directory; its `.gcloudignore` excludes everything except the Dockerfile, build configuration, and [preparation helper](../containers/gcp-gguf-inference/prepare_context.py). Inside a regional Cloud Build, the helper downloads the existing candidate tar from `gs://edugraph-classify` at GCS generation `1791147881432887`. It checks its 17,478,901,760-byte length and full SHA-256 `7fc4a0f8fc21761615751107e92b44ffe4f9f75a9cde3aaac6613e4d51c33c72`, rejects missing, extra, duplicate, or non-regular tar members, and verifies the six recipe-pinned member hashes. It stages only `model-Q4_K_M.gguf`, `mmproj-BF16.gguf`, `chat_template.jinja`, and the source-controlled Dockerfile in the build context. The Dockerfile checks the three staged hashes again. A missing or replaced GCS generation fails closed. No large local upload, floating model URL, or full-archive extraction enters the build.

The build requires a newly reviewed, immutable 40-hex-character Hub commit, passed explicitly as `_MODEL_HF_REVISION`; the helper checks its shape before downloading and the Dockerfile records it in an OCI label. The config tags `europe-west4-docker.pkg.dev/edugraph-438718/edugraph-predict/qwen38-27b-gguf:<Hub revision>`; Cloud Build's `images` field pushes it once and records it in the build result. It requests Google's [recommended large-model image-build resources](https://docs.cloud.google.com/run/docs/configuring/services/gpu-best-practices): `E2_HIGHCPU_32`, 500 GB disk, and a two-hour timeout. At [current Netherlands Cloud Build rates](https://cloud.google.com/build/pricing-update), the two-hour ceiling is about **$8.06** for compute and disk (32-CPU build at $0.06552/minute, plus 400 GB billable SSD above the first 100 GB), before Artifact Registry storage, logs, taxes, or other service charges. The image itself will add roughly the GGUF payload size plus runtime layers to billed Artifact Registry storage. Google recommends Cloud Storage startup loading for models over 10 GB, so measure import/cold-start behavior before making this image-embedded canary route permanent.

The `edugraph-predict` Docker repository already exists in `europe-west4`, the `edugraph-classify` bucket is also in `europe-west4`, and a read-only check found the Cloud Build API enabled; no repository or bucket creation is needed. Stage the four small source files under `gs://edugraph-classify/cloud-build-source/` so the same dedicated build service account can read both the source and existing candidate using `roles/storage.objectViewer` on that bucket. Grant `roles/artifactregistry.writer` only on the retained `edugraph-predict` repository and `roles/logging.logWriter` for `CLOUD_LOGGING_ONLY` logs. The submitter needs Cloud Build build-creation rights, source-staging upload rights, and `iam.serviceAccounts.actAs` on that build account. Google [requires an explicit supported log destination](https://docs.cloud.google.com/build/docs/securing-builds/configure-user-specified-service-accounts) for a user-managed build account. Review the account, source commit, final Hub revision, IAM, estimated cost, and command before execution; `AGENTS.md` requires explicit provider-cost approval. The prepared command is:

```powershell
gcloud builds submit containers/gcp-gguf-inference `
  --config containers/gcp-gguf-inference/cloudbuild.yaml `
  --project edugraph-438718 --region europe-west4 `
  --gcs-source-staging-dir gs://edugraph-classify/cloud-build-source/ `
  --service-account projects/edugraph-438718/serviceAccounts/<reviewed-build-service-account> `
  --substitutions '_MODEL_HF_REVISION=<immutable-40-hex-Hub-commit>'
```

After a successful build, read the image digest independently from [Artifact Registry](https://docs.cloud.google.com/artifact-registry/docs/docker/manage-images) with `gcloud artifacts docker images describe <tagged-image> --format=json`, compare it to the Cloud Build result, and deploy the `@sha256:<digest>` reference. Read back the new revision's image digest and traffic allocation after deployment. Do not deploy the mutable tag.

## No-traffic GCP canary and rollback

After release verification and explicit provider approval, build and push an image tagged with the reviewed Hub revision, record its Artifact Registry digest, and deploy that digest as a tagged **no-traffic** `edugraph-predict` revision. Start at Cloud Run concurrency one and the Dockerfile's 2,048-token context. Preserve scale-to-zero, maximum one instance, existing service identity and access controls. Confirm GPU load, GPU and host memory, cold start, model health, exact request/response compatibility and latency via the tagged URL. The RunPod L40S peak was 18,840 MiB, below the L4's nominal 24 GB, but it does not prove Cloud Run L4 fit. The existing 16 GiB host-memory setting and 30-second Imagine client timeout also need validation. Google documents [L4 memory and service requirements](https://docs.cloud.google.com/run/docs/configuring/services/gpu) and [tagged no-traffic rollouts](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

Canary Imagine's classification-only backend and matching web build against the tagged prediction revision before moving any public traffic. Check image upload through `/classify`, complete v0.30 identifiers and response mapping, visible controls, errors, and latency. The 4B model's old dataset and ontology make a paired old-versus-new score unnecessary for this promotion; the pinned GGUF validation and end-to-end canary checks are the quality and compatibility evidence. Then shift a controlled fraction of traffic, inspect errors and latency, and move to 100% only when end-to-end behavior is sound. Keep both old revisions and digests. If the new path fails, route `edugraph-predict` back to `edugraph-predict-00005-59s` and Imagine back to its previous revision/contract; verify both surfaces after rollback. Creating the image or revision, sending GPU canary requests, publishing to Hub, and shifting deployment traffic are provider operations requiring user confirmation under `AGENTS.md`.
