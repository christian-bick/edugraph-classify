# Imagine baseline promotion: Qwen3.8-27B GGUF

This is the promotion path for the verified EduGraph classifier candidate and the chosen classification-only Imagine rollout. It records the public model release, completed prediction canary, and remaining GCP cutover gates; it does not authorize another provider operation. The public `edugraph-predict` traffic remains 100% on the 4B GGUF revision `edugraph-predict-00005-59s`, image digest `sha256:6c0080fc4ff1ddda4295916a44ec6cc8e715ab3d01d3b5172b7def6c5cdfb9f0`. The new `edugraph-predict-00006-nej` L4 revision is healthy under the `qwen38-canary` tag with 0% public traffic. The old revision and digest remain the rollback anchor.

Future Apache-2.0 EduGraph weight releases still require verification of their own exact upstream license and redistribution terms.
2. ## Serving and application contract

The new [production Dockerfile](../containers/gcp-gguf-inference/Dockerfile) builds the same pinned llama.cpp release and verifies the language GGUF, projector and template at image-build time. Its default server flags match the benchmark's concurrency-one route: 2,048 context tokens per slot, 1,024 microbatch, one slot, all GPU layers, `--fit off`, and the fixed Jinja template. The Cloud Build helper stages only the verified model, projector, template, and Dockerfile from the generation-pinned GCS archive as its context, so no remote `ADD` or floating model URL enters the image. The large image is a deliberate first canary route compatible with the current production pattern; Google [recommends Cloud Storage for models of this size](https://docs.cloud.google.com/run/docs/configuring/services/gpu-best-practices), so cold-start/import time and storage cost must be measured before adopting it as the permanent path.

Imagine currently sends an image-only request and expects uppercase `Area`, `Scope`, `Ability` keys. The validated request instead contains `prompt.json`'s user text, an RGB JPEG quality-75 image data URL, an ordered copy of `closed_schema.json` with `areas, scopes, abilities`, temperature zero, `max_tokens=512`, `enable_thinking=false`, and no stream. The client must validate lowercase identifiers against ontology v0.30.0 and adapt them to the existing URI-bearing application response. Keep this new contract opt-in through the paired Imagine backend and web canary and an explicit traffic cutover; the deployed 4B contract must continue to work.

Imagine currently loads ontology v0.5.0 and an old embedding model/entity map. In the GGUF v4 reference round, 88 of 126 distinct predicted identifiers were absent from v0.5.0 and every case had at least one absent identifier. The immutable [v0.30.0 ontology release](https://github.com/christian-bick/edugraph-ontology/releases/download/v0.30.0/core-ontology-math.rdf), SHA-256 `6372ccb30056aac760a3883f933cdfc6b1bbf563a68aeecd5f03a03da3f3bdcb`, contains all 680 schema labels; its individual URIs use `http://edugraph.io/edu/<Label>` rather than the legacy `http://edugraph.io/edu#<Label>`. Validate and display all predicted identifiers under this ontology; do not silently drop new ones or treat unrelated ontology relations as logical entailment.

The currently served Imagine web bundle sends uploads to `/classify_and_search` and offers Find Similar through `/search`, so the public demo does invoke the embedding-backed path today. The chosen update is classification-only: promote the isolated backend's opt-in GGUF request and v0.30 ontology contracts with `SEARCH_MODE=disabled`, then ship the matching opt-in web build that calls `/classify` and hides Find Similar. Both components must move together; disabling backend search alone would make the current web upload flow fail. The local classification-only canary package pins and verifies the prompt, schema, and RDF without requiring an embedding or content index. Neither isolated branch has been deployed. Rebuilding and evaluating a compatible embedding and content index is a separate future task and does not block the classifier publication or classification-only canary.

## Cloud Build and image verification

The model release is public. The first Cloud Build submission on 2026-10-06 uploaded only its 9.3 KiB source archive and was rejected with `FAILED_PRECONDITION` before a build was allocated: the project has a 10-CPU regional default-pool quota, so `E2_HIGHCPU_32` cannot run in `europe-west4`. Build `1826501d-e188-4438-b6f2-189247b2e9fd` then started on the 8-CPU worker but failed in its first step, before model download: the minimal Cloud CLI `stable` image had no `python3` executable in `PATH`. The preparation step now uses the official Python-capable `slim` image pinned to OCI index digest `sha256:be4876b4311056bf3ce236a14a7dea1288e70b7cfea2454ea15e4165c819921f`; its [source Dockerfile](https://github.com/GoogleCloudPlatform/cloud-sdk-docker/blob/master/debian_slim/Dockerfile) installs and checks Python. The corrected build and no-traffic canary subsequently succeeded; the first two failures did not produce an image or revision.

The local Docker daemon is unavailable. The reviewed [Cloud Build configuration](../containers/gcp-gguf-inference/cloudbuild.yaml) submits only the small `containers/gcp-gguf-inference` directory; its `.gcloudignore` excludes everything except the Dockerfile, build configuration, and [preparation helper](../containers/gcp-gguf-inference/prepare_context.py). Inside a regional Cloud Build, the helper downloads the existing candidate tar from `gs://edugraph-classify` at GCS generation `1791147881432887`. It checks its 17,478,901,760-byte length and full SHA-256 `7fc4a0f8fc21761615751107e92b44ffe4f9f75a9cde3aaac6613e4d51c33c72`, rejects missing, extra, duplicate, or non-regular tar members, and verifies the six recipe-pinned member hashes. It stages only `model-Q4_K_M.gguf`, `mmproj-BF16.gguf`, `chat_template.jinja`, and the source-controlled Dockerfile in the build context. The Dockerfile checks the three staged hashes again. A missing or replaced GCS generation fails closed. No large local upload, floating model URL, or full-archive extraction enters the build.

The build requires the verified immutable Hub commit `477e3caf32eced2a9e002ead1edccc9a5c458f0c`, passed explicitly as `_MODEL_HF_REVISION`; the helper and Dockerfile both require that exact published revision before building, and the Dockerfile records it in an OCI label. The config tags `europe-west4-docker.pkg.dev/edugraph-438718/edugraph-predict/qwen38-27b-gguf:<Hub revision>`; Cloud Build's `images` field pushes it once and records it in the build result. The successful build used `E2_HIGHCPU_8`, 500 GB disk, and the same two-hour timeout, fitting the project's 10-CPU [regional default-pool quota](https://docs.cloud.google.com/build/quotas). CUDA compilation is limited to two parallel jobs to fit the worker's 8 GB RAM. At [current Netherlands Cloud Build rates](https://cloud.google.com/build/pricing-update), the two-hour ceiling is about **$2.16** for compute and disk (8-CPU build at $0.01638/minute, plus 400 GB billable SSD above the first 100 GB), before Artifact Registry storage, logs, taxes, or other service charges. ## No-traffic GCP canary and rollback

On 2026-10-06 the approved `edugraph-predict-00006-nej` canary deployed from the verified digest with one L4, 4 CPU, 16 GiB host RAM, concurrency one, zero minimum and one maximum instance, the existing runtime service account and private invoker policy. The `qwen38-canary` tag has 0% public traffic; `edugraph-predict-00005-59s` retains 100%. Cloud Run took 11m47s to import the 17.5 GB image and 30s to mark its container healthy. This import delay supports evaluating a Cloud Storage startup-load path for future model updates.

One private request recreated the pinned GGUF v4 benchmark payload (SHA-256 `f0e681f179afd154d733e5dc2c4635750234424989a45b5c0cc979692a10c6e0`) and returned HTTP 200 with the expected exact labels, valid closed schema, `finish_reason=stop`, 465 prompt tokens and 24 completion tokens. Cloud Run recorded 34.009s request latency; the local client measured 36.0s. llama.cpp loaded the model in about 24s on scale-from-zero, then spent 2.243s on prompt evaluation and 1.707s on generation. Cloud Monitoring sampled up to 17,867,735,040 bytes (16.64 GiB) GPU memory and 912,801,792 bytes (0.85 GiB) host memory on this revision, fitting the L4 and 16 GiB host limit for this single request. The temporary scoped ID-token grant used for the private smoke was removed and its absence verified. This is a compatibility smoke, not an estimate of validation accuracy or production latency distribution. The client harness retained the parsed response labels and usage, but not the exact raw HTTP response body; the pinned v4 benchmark report retains raw responses for the full 64-case validation run. The opt-in classification-only Imagine backend already allows 240s for this model, while the legacy path retains 30s. Neither Imagine backend nor web has been deployed.

Canary Imagine's classification-only backend and matching web build against the tagged prediction revision before moving any public traffic. Check image upload through `/classify`, complete v0.30 identifiers and response mapping, visible controls, errors, and latency. The 4B model's old dataset and ontology make a paired old-versus-new score unnecessary for this promotion; the pinned GGUF validation and end-to-end canary checks are the quality and compatibility evidence. Then shift a controlled fraction of traffic, inspect errors and latency, and move to 100% only when end-to-end behavior is sound. Keep both old revisions and digests. If the new path fails, route `edugraph-predict` back to `edugraph-predict-00005-59s` and Imagine back to its previous revision/contract; verify both surfaces after rollback. Creating the image or revision, sending GPU canary requests, publishing to Hub, and shifting deployment traffic are provider operations requiring user confirmation under `AGENTS.md`.
