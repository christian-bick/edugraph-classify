# Imagine baseline promotion: Qwen3.8-27B GGUF

This is the proposed promotion path for the verified EduGraph classifier candidate. It records local preparation and the gates for a public model release and a GCP cutover; it does not authorize a provider operation. The current `edugraph-predict` revision remains `edugraph-predict-00005-59s` on the 4B GGUF, with 100% of traffic and image digest `sha256:6c0080fc4ff1ddda4295916a44ec6cc8e715ab3d01d3b5172b7def6c5cdfb9f0` as the rollback anchor.

## Release gates

1. Confirm the model-weight license and public visibility. The old 4B model's AGPL license is not automatically inherited by this separate release. Do not publish an internal training manifest or a raw benchmark archive as the Hub repo.
2. Download the candidate with approved GCS egress, verify full archive bytes and SHA-256, then stage only the two GGUFs, chat template, prompt, closed schema, model card, license and sanitized provenance. Independently verify the hashes of all staged files. This is a separate step from Hub publication.
3. Review the card for intended use, limitations, exact validation cohort, all three stage scores, prompt/schema order, disabled thinking, JPEG image rendering, `max_tokens=512`, quantization, base/dataset/ontology/runtime pins, and matching projector. Upload only after approval; read back the Hub revision and file hashes. Retain the immutable revision in the build record.

## Serving and application contract

The new [production Dockerfile](../containers/gcp-gguf-inference/Dockerfile) builds the same pinned llama.cpp release and verifies the language GGUF, projector and template at image-build time. Its default server flags match the benchmark's concurrency-one route: 2,048 context tokens per slot, 1,024 microbatch, one slot, all GPU layers, `--fit off`, and the fixed Jinja template. Build with the curated release directory as the context so no remote `ADD` or floating model URL enters the image. The large image is a deliberate first canary route compatible with the current production pattern; Google [recommends Cloud Storage for models of this size](https://docs.cloud.google.com/run/docs/configuring/services/gpu-best-practices), so cold-start/import time and storage cost must be measured before adopting it as the permanent path.

Imagine currently sends an image-only request and expects uppercase `Area`, `Scope`, `Ability` keys. The validated request instead contains `prompt.json`'s user text, an RGB JPEG quality-75 image data URL, an ordered copy of `closed_schema.json` with `areas, scopes, abilities`, temperature zero, `max_tokens=512`, `enable_thinking=false`, and no stream. The client must validate lowercase identifiers against ontology v0.30.0 and adapt them to the existing URI-bearing application response. Keep this new contract opt-in until the new prediction revision is ready; the deployed 4B contract must continue to work.

Imagine also loads ontology v0.5.0 and an old embedding model/entity map for `/classify_and_search`. In the GGUF v4 reference round, 88 of 126 distinct predicted identifiers were absent from v0.5.0 and every case had at least one absent identifier. The immutable [v0.30.0 ontology release](https://github.com/christian-bick/edugraph-ontology/releases/download/v0.30.0/core-ontology-math.rdf), SHA-256 `6372ccb30056aac760a3883f933cdfc6b1bbf563a68aeecd5f03a03da3f3bdcb`, contains all 680 schema labels; its individual URIs use `http://edugraph.io/edu/<Label>` rather than the legacy `http://edugraph.io/edu#<Label>`. The existing embedding has zero exact URI overlap and covers only 38 of the 126 GGUF-predicted labels even after comparing names. Its index cannot serve the new model faithfully. Rebuild and pin the embedding and content vector index together before enabling search, or explicitly disable search for a classification-first rollout. Do not silently drop new identifiers from the displayed prediction or treat unrelated ontology relations as logical entailment.

The isolated Imagine backend branch has opt-in classifier and ontology contracts, checks the pinned prompt/schema and ontology release, and returns an explicit error when the current embedding lacks an entity. It also has a strict local index builder that requires a SHA-pinned content snapshot and a complete v0.30 embedding map; startup verifies that the resulting index uses the same embedding files as queries. The isolated web branch refetches the ontology on page load, clears stale search session state, and accepts either slash or hash individual URIs in search filters. Neither branch has been deployed. The default backend image still fetches a floating embedding and builds the legacy index, so it cannot serve a full-search canary. A separate classification-only canary package now pins and verifies the prompt, schema and RDF while disabling search explicitly; the opt-in web build calls `/classify` and hides Find Similar. Both paths preserve their legacy defaults.

A local v0.30 embedding candidate now covers all 766 ontology individuals, and a strict ten-item fixture index built with it. The stored vectors match the biased ONNX output exactly. This fixture contains only three unique label sets, however, and a broader ontology-edge probe placed just 191 of 1,500 directly related endpoints in the nearest ten under Imagine's Euclidean search distance. `Square` to its directly related `Rectangle` ranked 133rd. These probes are not a content-retrieval benchmark, but they make a public full-search switch unjustified without a varied, judged sample and the complete content index. Keep the existing public search path until that gate passes, or explicitly offer a classification-only experience that calls `/classify` and marks Find Similar unavailable. A no-traffic predictor canary and Hugging Face release can proceed independently of that product choice.

## No-traffic GCP canary and rollback

After release verification and explicit provider approval, build and push an image tagged with the reviewed Hub revision, record its Artifact Registry digest, and deploy that digest as a tagged **no-traffic** `edugraph-predict` revision. Start at Cloud Run concurrency one and the Dockerfile's 2,048-token context. Preserve scale-to-zero, maximum one instance, existing service identity and access controls. Confirm GPU load, GPU and host memory, cold start, model health, exact request/response compatibility and latency via the tagged URL. The RunPod L40S peak was 18,840 MiB, below the L4's nominal 24 GB, but it does not prove Cloud Run L4 fit. The existing 16 GiB host-memory setting and 30-second Imagine client timeout also need validation. Google documents [L4 memory and service requirements](https://docs.cloud.google.com/run/docs/configuring/services/gpu) and [tagged no-traffic rollouts](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

Canary Imagine with its new contract, ontology and a compatible search path against that tagged prediction revision before moving any public traffic. Measure the same 64 images against the existing deployed 4B revision if a paired old-versus-new quality claim is needed; the GGUF benchmark alone does not establish that comparison. Then shift a controlled fraction of traffic, inspect errors and latency, and move to 100% only when end-to-end behavior is sound. Keep both old revisions and digests. If the new path fails, route `edugraph-predict` back to `edugraph-predict-00005-59s` and Imagine back to its previous revision/contract; verify both surfaces after rollback. Creating the image or revision, sending GPU canary requests, publishing to Hub, and shifting deployment traffic are provider operations requiring user confirmation under `AGENTS.md`.
